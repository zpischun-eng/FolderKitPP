# FolderKit 동기화 알고리즘 분석 — 폴더 mtime 스킵을 적용하지 않은 이유

대상: `src/sync_core.py`

## 1. 현재 알고리즘

`scan()`이 좌/우 루트를 각각 재귀적으로 훑어 `{상대경로: FileInfo(size, mtime)}`
딕셔너리를 만들고, `classify()`가 두 딕셔너리를 합집합 키 기준으로 비교해
`ONLY_L / ONLY_R / NEWER_L / NEWER_R / SAME / CONFLICT` 상태를 매긴다.

**현재는 파일 단위로만 검사한다.** 폴더의 갱신 날짜를 보고 하위 전체를
건너뛰는 로직은 전혀 없다 — 모든 파일이 매번 `stat()` 대상이다.

## 2. "상위 폴더 mtime을 보고 건너뛸 수 있는가?" — 실험 결과

다음 전제가 성립해야 이 최적화가 안전하다: *"하위 폴더/파일이 바뀌면
그 조상 폴더의 mtime도 함께 바뀐다."* 컨테이너에서 직접 확인했다.

```
mtimetest/A/B/C/file.txt 생성 후 1.2초 대기

[1] file.txt '내용만' 수정 (이름 변경 없음)
    A  mtime 변경됨? False
    B  mtime 변경됨? False
    C  mtime 변경됨? False   ← 파일을 담고 있는 폴더조차 안 바뀜

[2] C 안에 새 파일 추가
    A  mtime 변경됨? False
    B  mtime 변경됨? False
    C  mtime 변경됨? True   ← 직속 부모만 바뀌고 위로는 전파 안 됨
```

**결론(모든 주요 파일시스템에 공통되는 표준 동작):**
- 폴더 mtime은 그 폴더의 **직속 항목 목록**이 바뀔 때만(생성/삭제/이름변경)
  갱신된다. **파일 내용 수정은 담고 있는 폴더의 mtime에 아무 영향을 주지
  않는다.**
- 폴더 mtime 변경은 **위로 전파되지 않는다.** `A/B/C`가 바뀌어도 `B`, `A`는
  그대로다.

## 3. 왜 적용하지 않았는가

이 두 사실 때문에, "최상위 폴더 mtime만 보고 하위 전체 스킵"은 다음을
놓칠 수 있다:
- 하위 폴더 안 파일의 **내용 수정** (거의 모든 실사용 시나리오의 핵심)
- 두 단계 이상 깊은 곳에서 일어난 추가/삭제

동기화/백업 도구에서 이런 누락은 "느림"보다 훨씬 심각한 **무음 데이터
유실**이다. 그래서 이번에는 이 방식을 구현하지 않았다.

## 4. 대신 적용한 안전한 개선

1. **`os.scandir()` 기반 스캔** — 기존 `os.walk()` + 파일마다 별도
   `os.stat()` 대신, `os.scandir()`의 `DirEntry`가 돌려주는 stat 캐시를
   그대로 쓴다. 시스템 콜을 줄여 특히 파일 수가 많을 때 유리하다.
   심볼릭 링크 동작(파일은 따라가서 stat, 디렉터리는 목록에는 있지만
   내려가지 않음)은 기존과 완전히 동일하게 맞췄고, 합성 테스트 트리로
   결과가 100% 일치함을 확인했다.
2. **좌/우 스캔 병렬화** — `ScanThread`가 좌·우를 순차가 아니라
   `ThreadPoolExecutor`로 동시에 스캔한다. 두 폴더가 서로 다른 물리
   드라이브(로컬 ↔ 외장/네트워크 등)에 있을 때 실질적인 단축 효과가 있고,
   같은 드라이브라도 손해는 없다(각 파일 I/O 자체가 매우 가벼움).

## 5. 검증

- 심볼릭 링크·제외 패턴이 섞인 합성 트리에서 기존 `scan()`과 신규 `scan()`의
  결과가 완전히 동일함을 확인(재귀/비재귀 모두).
- 약 4,000개 파일 트리에서 `ScanThread`를 실제로 실행해 분류 결과
  (`SAME`/`ONLY_L`/... 개수)가 기대와 일치함을 확인.
- `plan_actions()` / `decide()` / `classify()`는 변경하지 않았다 — 정책
  로직은 그대로이므로 동기화 동작 자체(무엇을 복사/삭제할지)는 v38과
  100% 동일하다.

## 6. 더 근본적인 해법(참고, 이번 범위 밖)

정말로 "이미 동기화된 상태에서 재스캔이 거의 즉시 끝나야 한다"는 요구가
있다면, 올바른 해법은 폴더 mtime 휴리스틱이 아니라 **이전 스캔 결과를
저장해 두는 인덱스/캐시**다. rsync, Unison, 각종 클라우드 동기화 클라이언트가
쓰는 방식과 같다:
- 이전 스캔 시점의 (경로, 크기, mtime)을 로컬에 저장해 두고
- OS의 파일 변경 알림(Linux inotify, macOS FSEvents, Windows
  ReadDirectoryChangesW)을 백그라운드에서 구독해 실제로 무엇이 바뀌었는지
  실시간으로 알아내거나
- 최소한 저장된 이전 스캔 결과와 비교해 "이 파일은 마지막 스캔 이후
  안 바뀐 것 같다"는 판단을 mtime 하나가 아니라 (크기+mtime) 조합으로
  더 신뢰성 있게 내리는 것

이 방식은 실시간 감시 프로세스 관리, 프로그램이 꺼져 있는 동안의 변경
처리 등 설계가 커지는 작업이라 이번 범위에서는 진행하지 않았다.
