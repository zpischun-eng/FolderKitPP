# FolderKit 중복 파일 찾기 — 원리 분석과 속도 개선 방안

대상: `src/duplicate_finder.py` (v37) · 검토 환경: 총 7.26TB / 5개 폴더 / 동영상 위주

---

## 1. 현재 v37 알고리즘의 원리

선생님이 알고 계신 내용이 정확합니다. `DuplicateScanThread.run()`은 **"싼 검사로 후보를 좁히고, 비싼 검사는 살아남은 것에만"** 이라는 전형적인 다단계 필터 구조입니다.

### 1단계 — 파일 수집
```python
for dirpath, dirnames, filenames in os.walk(root):
    dirnames[:] = [d for d in dirnames if not is_excluded(d)]
```
`os.walk`로 하위 폴더를 전부 훑고, `seen` 집합으로 등록 폴더가 겹칠 때의 중복 집계를 막습니다.

### 2단계 — 파일 크기로 1차 그룹화
```python
by_size[os.path.getsize(p)].append(p)
size_groups = {sz: paths for sz, paths in by_size.items() if len(paths) > 1}
```
**핵심 원리**: 내용이 같으면 크기는 반드시 같습니다. 대우를 취하면 *크기가 다르면 내용은 절대 같을 수 없다*. 파일을 1바이트도 읽지 않고 후보를 걸러내므로 비용이 사실상 0입니다. 크기 그룹의 원소가 1개면 그 파일은 중복이 될 수 없으니 즉시 탈락합니다.

### 3단계 — 앞 64KB 부분 해시로 2차 그룹화
```python
PARTIAL_HASH_BYTES = 65536
by_partial[_hash_file(p, max_bytes=PARTIAL_HASH_BYTES)].append(p)
```
크기가 같은 파일들끼리만 앞 64KB를 읽어 MD5를 구합니다. 여기서도 **앞부분이 다르면 전체가 다르다**는 필요조건을 씁니다. 4GB 동영상이라도 64KB만 읽으므로 파일당 비용이 6만 분의 1로 줄어듭니다.

### 4단계 — 전체 해시로 최종 확정
```python
by_full[_hash_file(p)].append(p)   # 1MB씩 끝까지 읽어 MD5
```
크기와 앞 64KB가 모두 같은 후보들만 파일 전체를 읽어 MD5를 계산하고, 해시가 같으면 같은 `DuplicateGroup`으로 묶습니다.

## 2. 병목이 어디인가

측정을 위해 동영상 컬렉션을 흉내 낸 테스트 세트(600MB짜리 7개 = 4.4GB, 진짜 중복 2쌍 포함)를 만들어 v37을 계측했습니다.

| | 디스크에서 읽은 양 |
|---|---|
| 디스크 위의 데이터 총량 | 4,404 MB |
| **v37이 실제로 읽은 양** | **3,775 MB (86%)** |

**4단계가 전부입니다.** 1~3단계가 읽는 양은 파일당 64KB로 무시할 수준이고, 시간의 99% 이상이 "전체 해시"에서 나옵니다.

문제의 본질은 이겁니다. **3단계를 통과한 파일들은 대부분 진짜 중복입니다.** 중복 파일을 찾는 게 목적이니 당연한 결과인데, 그 결과 4단계는 "중복인 파일 전체를 빠짐없이 다 읽는" 단계가 됩니다. 중복이 100GB 있으면 100GB를 그대로 읽습니다.

### 7.26TB 환산 (HDD 150MB/s 가정)

후보로 분류되는 비율을 30%로만 잡아도 2.2TB를 읽어야 합니다.

```
2.2 TB ÷ 150 MB/s ≈ 14,600초 ≈ 4시간
```

후보 비율이 60%면 8시간입니다. 선생님이 겪고 계신 "매우 오래 걸림"이 정확히 이 계산과 맞습니다.

### 부수적인 병목 4가지

1. **`os.walk` + `os.path.getsize`의 이중 stat** — `os.walk`는 내부적으로 `scandir`가 이미 읽어 온 크기 정보를 버리고, 뒤에서 `getsize()`가 파일마다 stat을 다시 호출합니다. 파일이 많을수록 손해입니다.

2. **MD5 선택** — 이 환경에서 측정한 해시 처리량입니다.
   | 알고리즘 | 처리량 |
   |---|---|
   | MD5 (현재) | 583 MB/s |
   | BLAKE2b | 592 MB/s |
   | SHA-1 (SHA-NI 가속) | 1,461 MB/s |
   | **xxh3_128** | **6,589 MB/s** |

   MD5는 요즘 CPU에서 오히려 느린 축입니다. NVMe(3,000MB/s+)에서는 MD5가 진짜 병목이 됩니다.

3. **`progress` 시그널 폭주** — 파일마다 시그널을 쏘고, 슬롯이 `logmsg()`로 콘솔 위젯에 계속 append합니다. 파일 수만 개면 UI 스레드가 이것만 처리하다 밀립니다. 진행률을 *파일 수*로 세는 것도 문제인데, 4GB 파일과 4KB 파일이 똑같이 1로 세어져 진행률 바가 의미를 잃습니다.

4. **⚠️ 2GB 오버플로 버그 (실제로 확인)** — 개선판을 만들며 바이트 단위 진행률을 넣었더니 이 예외가 났습니다.
   ```
   RuntimeWarning: libshiboken: Overflow: Value 3876388864 exceeds limits
                   of type [signed] "i" (4bytes)
   OverflowError
   ```
   `Signal(int, int, str)`의 `int`는 파이썬 int가 아니라 **C의 32비트 int**로 매핑됩니다. 2,147,483,647을 넘으면 터집니다. 지금 v37은 파일 *개수*를 보내므로 우연히 무사하지만, 바이트를 다루는 순간 TB급에서 반드시 터집니다. `Signal('qlonglong', 'qlonglong', str)`로 바꿔야 합니다.

## 3. 질문하신 "폴더별 스레드"에 대한 평가

결론부터 말씀드리면 **방향은 맞지만 나누는 축이 잘못됐습니다.** 세 가지 이유입니다.

### (1) 폴더는 부하가 균등하지 않습니다
선생님 폴더는 3.57 / 2.37 / 0.78 / 0.28 / 0.26 TB입니다. 폴더당 스레드 1개면 5개 스레드 중 4개가 놀고 3.57TB 스레드 하나를 기다립니다. **전체 시간이 가장 큰 폴더 하나의 시간과 같아집니다.** 7.26TB 작업이 3.57TB 작업이 된 것뿐이라 이론상 최대 2배 개선에 그칩니다.

### (2) 중복은 폴더 경계를 넘나듭니다
폴더별로 독립 처리하면 A폴더 파일과 B폴더 파일이 같은지 판정할 수 없습니다. 폴더별로 해시만 병렬로 구하고 마지막에 합치는 건 가능하지만, 그건 이미 폴더가 아니라 *파일 단위 병렬화*입니다.

### (3) ★가장 중요 — HDD에서는 스레드를 늘리면 느려집니다
7.26TB면 거의 확실히 HDD입니다. HDD는 물리적 헤드가 하나뿐이라 여러 스레드가 서로 다른 위치를 동시에 요청하면 헤드가 왔다 갔다 하며 **탐색 시간(seek)이 순차 읽기 시간을 잡아먹습니다.** 순차 150MB/s가 랜덤 접근에서 5MB/s 밑으로 떨어지는 일이 흔합니다.

| 저장장치 | 권장 동시 읽기 |
|---|---|
| HDD | **1~2** (더 늘리면 역효과) |
| SATA SSD | 4~6 |
| NVMe | 6~8 |
| NAS / 네트워크 드라이브 | 8~16 (지연 숨기기) |

**올바른 병렬화 축**: 폴더가 아니라 **물리 장치(`st_dev`)**입니다. 여러 드라이브에 걸쳐 있으면 드라이브별로 동시에 진행하되, **한 드라이브 안에서는 동시 읽기 수를 제한**해야 합니다.

참고로 파이썬 GIL은 여기서 문제가 되지 않습니다. `hashlib`은 2KB 이상 버퍼를 처리할 때 GIL을 놓기 때문에 스레드만으로 진짜 병렬 해싱이 됩니다. `multiprocessing`까지 갈 필요 없습니다.

**그리고 병렬화는 이 문제의 정답이 아닙니다.** HDD 대역폭이 이미 포화 상태이므로 스레드를 늘려도 150MB/s는 그대로입니다. 진짜 해법은 **읽는 양 자체를 줄이는 것**입니다.

## 4. 개선 설계 — 읽는 양을 줄이는 것이 핵심

### 새 파이프라인

| 단계 | 내용 | 파일당 비용 |
|---|---|---|
| 0 | `os.scandir`로 크기·mtime·dev/ino 동시 수집 | **0** (추가 I/O 없음) |
| 1 | 크기 그룹화 | **0** |
| 2 | 하드링크 접기 `(dev, ino)` ★신규 | **0** |
| 3 | 앞 64KB 해시 | 64 KB |
| 4 | **뒤 64KB 해시** ★신규 | 64 KB |
| 5 | **샘플 해시 (전체에 흩뿌린 16 × 1MB)** ★신규 | 16 MB |
| 6 | 전체 해시 (엄격 모드에서만) | 파일 전체 |

**4단계(뒤 64KB)** 는 비용이 seek 한 번인데 효과가 큽니다. 동영상은 컨테이너 헤더가 같아 앞 64KB가 우연히 일치하는 일이 잦은데, 끝부분은 인코딩 결과가 그대로 반영되므로 재인코딩본이 여기서 대부분 걸러집니다.

**5단계(샘플 해시)** 가 핵심입니다. 파일 전체에 균등하게 16개 지점을 잡아 1MB씩만 읽습니다.
- 4GB 동영상: 4,096MB → **16MB (0.4%, 약 250배 감소)**
- 크기 · 앞 64KB · 뒤 64KB · 흩뿌린 16MB가 전부 일치

### 그 외 개선
- **SQLite 해시 캐시** — `(경로, 크기, mtime)` 키로 해시를 저장. 파일이 그대로면 재스캔 시 디스크를 아예 읽지 않습니다.
- **장치별 동시 실행 제한** — `st_dev`별 세마포어. HDD는 2, SSD는 6, NAS는 8.
- **xxh3_128** (없으면 SHA-1로 대체) — MD5 대비 11배
- **`readinto()` + 재사용 버퍼** — TB급에서 블록마다 새 bytes를 만들지 않아 GC 부담 제거
- **바이트 기준 진행률 + 0.2초 스로틀** — UI 폭주 방지, 진행률이 실제 남은 작업량 반영
- **`qlonglong` 시그널** — 2GB 오버플로 버그 수정
- **같은 장치 안에서 경로 순 정렬 후 읽기** — HDD 헤드 이동 최소화

## 5. 실측 결과

동영상 컬렉션을 흉내 낸 4.4GB 세트(600MB × 7개, 진짜 중복 2쌍)에서 측정했습니다.

| | 시간 | **읽은 양** | 결과 |
|---|---|---|---|
| v37 (MD5, 전체 해시) | 7.32s | **3,775 MB** | 정확 |
| **v38 빠른 모드 (첫 스캔)** | 0.04s | **101 MB** | 오탐 1건 (아래 설명) |
| **v38 빠른 모드 (재스캔)** | 0.00s | **0 MB** | 캐시 적중 |
| v38 엄격 모드 | 1.10s | 3,876 MB | **v37과 완전 일치** |

- **읽는 양 37배 감소** (3,775 → 101 MB)
- **재스캔은 디스크를 전혀 읽지 않음** (0 MB)
- 엄격 모드는 v37과 결과가 비트 단위로 동일하면서 **6.7배 빠름** (xxh3 효과)

> 시간 수치는 OS 페이지 캐시가 더워진 상태라 실제 HDD보다 훨씬 짧게 나옵니다. **"읽은 양" 열이 실제 체감 속도를 대변하는 숫자**로 보시면 됩니다.

### 7.26TB 예상치 (HDD 150MB/s, 후보 비율 30% 가정)

| | 예상 소요 |
|---|---|
| 현재 v37 | **약 4시간** |
| v38 빠른 모드 (첫 스캔) | **약 10~15분** |
| v38 빠른 모드 (재스캔) | **1분 이내** |
| v38 엄격 모드 | 약 1.5~2시간 |

추정치이며 파일 개수·중복 비율·드라이브 상태에 따라 달라집니다. 다만 자릿수 수준의 개선은 확실합니다.

## 6. ⚠️ 빠른 모드의 한계 — 반드시 알고 쓰셔야 합니다

테스트에서 **의도적으로 만든 함정 파일**이 오탐으로 잡혔습니다.

```
크기 동일 · 앞 64KB 동일 · 뒤 64KB 동일 · 중간 300MB 지점의 16바이트만 다름
→ 빠른 모드: 중복으로 오판 ❌
→ 엄격 모드: 정확히 구분 ✓
```

샘플링은 파일의 0.4%만 보므로, **파일 중간의 아주 작은 구간만 다른 경우**를 놓칠 수 있습니다. 동영상에서는 중간에 박힌 챕터/자막/메타데이터 블록만 다른 경우가 여기 해당할 수 있습니다.

### 해법 — "빠른 스캔 + 삭제 직전 검증"

이게 제가 권하는 최종 구조입니다. `verify_group()` 함수를 같이 넣어 뒀습니다.

1. **스캔은 빠른 모드로** — 7.26TB를 10분에 훑어 중복 후보를 파악
2. **사용자가 지울 파일을 고름** — 보통 몇 개~몇십 개
3. **삭제 버튼을 누르면 그 그룹만 전체 해시로 재확인** — 대상이 적으니 비용이 작음
4. 검증에서 갈라지면 삭제를 중단하고 경고

되돌릴 수 없는 삭제의 안전성은 엄격 모드와 완전히 같으면서, 스캔 속도는 빠른 모드 그대로입니다. 실제로 함정 파일이 이 검증에서 정확히 걸러지는 것을 확인했습니다.

```
verify_group(['movie1.mkv', 'near.mkv'])  → [['movie1'], ['near']]   삭제 차단 ✓
verify_group(['movie0.mkv', 'copy0.mkv']) → [['movie0', 'copy0']]    삭제 승인 ✓
```

## 7. 적용 방법

`src/duplicate_finder.py`를 새 파일로 교체하면 됩니다. `DuplicateGroup`과 `DuplicateScanThread`의 시그널 규약, `DuplicatePreviewPopover`가 모두 그대로라 **`main_window.py` 수정 없이 동작합니다.**

다만 다음 두 가지는 손보시길 권합니다.

**(1) 콘솔 로그 줄이기** — `on_dupfind_progress`의 `logmsg` 호출이 여전히 부담입니다.
```python
def on_dupfind_progress(self, done, total, current_path):
    pct = int(done / total * 100) if total else 0
    self.progress.setValue(pct)
    self.overlay.set_progress(pct, "중복 파일 검사 중입니다…")
    if pct != getattr(self, "_dup_last_pct", -1):   # 1%마다만 기록
        self._dup_last_pct = pct
        self.logmsg(f"[중복찾기] {pct}% — {current_path}")
```

**(2) 삭제 직전 검증 연결** — 삭제 핸들러에서 `verify_group()`을 호출하도록.

옵션은 이렇게 줍니다.
```python
DuplicateScanThread(
    roots,
    strict=False,        # 기본 빠른 모드
    workers=2,           # HDD면 2, SSD면 6, None이면 자동
    use_cache=True,
    device_profile={},   # {st_dev: "hdd"|"ssd"|"net"} 수동 지정 가능
)
```

**설치 권장**: `pip install xxhash` — 없어도 SHA-1로 자동 대체되지만, 있으면 해싱이 11배 빨라집니다. `requirements.txt`에 `xxhash>=3.0`을 추가하시면 됩니다.

## 8. 요약

- 병목은 **4단계 전체 해시**이고, 시간의 99%가 여기서 나옵니다.
- **폴더별 스레드는 권하지 않습니다.** 부하 불균형(3.57TB 폴더가 전체를 결정)이 심하고, HDD에서는 스레드 증가가 오히려 느려지게 만듭니다. 병렬화는 폴더가 아니라 **물리 장치 단위**로, 그것도 **동시 수를 제한**해서 해야 합니다.
- 진짜 해법은 병렬화가 아니라 **읽는 양을 줄이는 것**입니다. 뒤 64KB + 샘플 해시로 4GB 파일당 읽기를 **250배** 줄였고, 실측 기준 전체 읽기량이 **37배** 감소했습니다.
- **해시 캐시**로 재스캔은 디스크 접근이 0이 됩니다.
